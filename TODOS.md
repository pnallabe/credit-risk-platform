## GAP-19: Anti-Hallucination Framework + Code Transparency Layer — P1 CRITICAL

**What:** Structural rewrite of the AI agent from a single LangChain ReAct loop
to a multi-agent pipeline that surfaces executable SQL and Python with every answer,
computes a confidence score, enforces a grounding gate (refuse when data is unavailable),
and stores `code_artifacts`, `result_hash`, `query_hash`, and `data_lineage_tags`
immutably per answer.

**Why:** This is the KEY DIFFERENTIATOR of ILOL vs. generic AI chatbots over portfolio
data. "Every AI answer carries executable SQL and Python — users never asked to trust
a number they cannot verify." Without this, the AI agent is a liability to an enterprise
customer: an OCC examiner asks "show me the code that produced this answer" and gets nothing.

**Pros:** Closes the single most important differentiator gap. Platform becomes
enterprise-ready. Exam packet AI appendix (GAP-21) becomes buildable.

**Cons:** 8-12 engineering days. Requires architecture design before sprinting.
The current single-agent code needs structural changes, not just field additions.

**Context:** `ai-agent/src/main.py` is the current agent. `compliance/prohibited_variables.py`
needs to be wired into the SQL validation path. The existing `audit/logger.py` hash-chain
pattern should be applied to AI answers. Start with architecture design: define the
`AgentResponse` schema (including `code_artifacts` array) before touching agent logic.

**Effort:** ~8-12 days human / ~2-3 days with CC+gstack
**Priority:** P1
**Depends on:** None (independent)
**Blocks:** GAP-21

## GAP-23: Manual Review / Referral Queue — ✅ CLOSED

**Status:** CLOSED — `decision-api/src/referral_store.py` implemented with full referral lifecycle (`pending → claimed → resolved | sla_breached`). Four-eyes enforcement on resolution (`resolved_by ≠ approved_by`). `DECISION_CONDITIONAL` already in `decision_engine/engine.py`. Routes in `decision-api/src/main.py`: `GET /v1/review/queue` (paginated, filterable), `POST /v1/review/{id}/claim`, `POST /v1/decisions/{id}/override` (APPROVE/REJECT/CONDITIONAL). SLA auto-breach on queue fetch. Override records written to `policy_overrides_log`.

**What:** The decision engine returns `MANUAL_REVIEW` (HTTP 202) but there is no API
surface for loan officers to find and resolve those applications. Need:
- `GET /v1/review/queue` (paginated, tenant-scoped, filterable by age)
- `POST /v1/review/{application_id}/claim` (assign reviewer identity)
- `POST /v1/decisions/{id}/override` (post-decision override: convert MANUAL_REVIEW →
  APPROVE/REJECT with justification → four-eyes → log to `policy_overrides_log`)
- `DECISION_CONDITIONAL` constant + conditional terms storage
- Referral SLA monitoring + alerting (analogous to `monitoring/tests/test_aa_deadline_alert.py`)

**Why:** Without a referral queue, MANUAL_REVIEW applications disappear into the DB.
Loan officers have no way to see, claim, or resolve them. Applications aging past the
Reg B 30-day window create CFPB adverse action exposure — the same rule enforced for
auto-declines is not enforced for referrals. PRD DE-007 requires `CONDITIONAL` outcome.

**Pros:** Independent of all other open gaps. ~4-6 days. Extends existing override pattern.
Required for any enterprise customer dealing with non-trivial referral volumes.

**Cons:** Changes the decision outcome enum — need to map `MANUAL_REVIEW` → `REFERRED`
per PRD schema terms and add `WITHDRAWN` handling. Check all downstream callers that
pattern-match on outcome strings.

**Context:** `audit/override_log.py` + `decision_engine/engine.py` `make_decision()` are
the starting points. The Reg B 30-day monitoring in `monitoring/tests/test_aa_deadline_alert.py`
is the pattern to follow for referral SLA alerting.

**Effort:** ~4-6 days human / ~1 day with CC+gstack
**Priority:** P2
**Depends on:** None (fully independent)
**Blocks:** Nothing
